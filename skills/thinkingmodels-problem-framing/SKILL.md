# ThinkingModels · 问题澄清

把困扰整理成一个能继续调查或行动的问题。沿用用户的目标、语境和语言；用户用英文提问就用英文回答。简单且清楚的任务直接处理，不强加完整框架，也不把澄清扩大成诊断、咨询项目或长期计划。

## 工作方式

1. **先还原，再改写。** 用一句话复述当前状态与用户希望发生的变化。把用户提出的解法和需要解释的现象分开；用户已明确选定的范围与约束不能悄悄替换。
2. **只整理影响下一步的信息。** 区分事实（材料或可核对的观察）、假设（尚未验证的解释）、约束（不能违反的边界）。必要时保留来源、时间与统计口径；缺失项写“未知”，不把用户的判断升级成事实。
3. **形成可处理的问题。** 说明对象、范围以及答案将影响的行动。例如把“用户为什么不喜欢我们”收窄为“哪些新用户在哪个环节停止，以及这会影响哪项改动”。无法合理确定的范围，提出一个有依据的暂定版本并标明。
4. **只追问真正阻塞的缺口。** 每轮最多一个问题；其余缺口作为待验证假设继续工作。若没有答案也能推进，就给可执行的下一步。不要为了填表逐项盘问。
5. **选择最小的信息动作。** 优先获取能区分两种解释的证据：核对一项口径、查看一段实际流程、访谈一个相关对象或做一次低成本观察。写清要看什么、结果如何改变下一步，以及何时回来看；不要默认获得访问系统或联系他人的授权。

需要时给一个最强的替代问题，解释它为什么可能改变行动。模型只是帮助提问的工具；没有明确帮助时，不推荐模型，也不进行“模型匹配”展示。

## 交付尺度

通常只需：**当前可用的问题 → 事实 / 假设 / 约束中的关键项 → 一个最小动作及其带回的证据**。用户要求深入时再展开。不能把“问题表述更清楚”报告成业务结果已经改善。

遇到把解法当问题、数据口径不明的情况，可读 [问题澄清示例](references/worked-example.md)。只有确实需要补充模型知识且已配置相关工具时，才读 [可选知识访问](references/knowledge-access.md)；离线即可完成本技能。
